## Provenance-lookup route taken (the brief's defect)

The brief's Step 5 hardcodes `getStrategyDossier('EMAcross')`. I did not copy that. Instead I
checked what the `Bot` record actually carries (`src/lib/types.ts`, `src/lib/queries.ts`):

- `Bot.family` is `'trend' | 'breakout' | 'mean-reversion' | 'carry' | 'market-neutral' | null`
  — a coarse **behavioural bucket**, not a strategy identifier. I confirmed in
  `src/lib/bot-params.ts` that many distinct screening bases (EMAcross, Donchian, ATRChannel,
  Chandelier, ADXRegime, BBSqueeze, ...) all fall under the same `family` value (e.g. "trend"),
  so `bot.family` cannot resolve a single `ScreeningCampaign.base` — it would either match the
  wrong campaign or match several.
- `Bot.strategy` is free-form display prose ("EMA 21 × EMA 55"...), not a stable identifier
  either.

Since the bot record genuinely carries nothing that identifies its specific screening base, I
took the brief's own fallback instruction: **look the bot up by its slug across all campaigns**,
via a new `bot_slug`-keyed query (`getProvenanceForBot`) rather than guessing a family. It queries
`screening_candidates` by `bot_slug` first (the join key `ScreeningCandidate.bot_slug` already
exists in the schema), then fetches the matching `screening_campaigns` row by `campaign_id`. This
is O(1) in query shape (2 point lookups) versus the brief's approach (fetch every campaign +
candidate for one hardcoded base and linear-scan for `bot.slug`), and it works for every bot
regardless of which base it came from — including bots the brief's approach would silently miss
today (e.g. `donchian-bf17`, `chandelier-bf14`, none of which are `EMAcross`).

Per the task instructions, this new query lives in `src/lib/screening.ts` (not inlined in the
page) with its own unit test in `tests/lib/screening.test.ts`.

## Self-review findings

- **Server component discipline**: `BotProvenance.tsx` has no `'use client'`, no hooks, no event
  handlers — confirmed by reading the file back. `page.tsx` remains an async server component;
  `getProvenanceForBot` is awaited server-side.
- **Forbidden-vocabulary test**: `/validé|gagnant|prouvé|survivant/i` — passes. No internal
  vocabulary (`GO_PAPER`, `MARGINAL`, `NO_GO`, `strong`) appears anywhere in the new component.
- **No parameter leakage**: the component only touches `ScreeningCampaign`/`ScreeningCandidate`
  scalar fields (counts, dates, `pf_net`/`null_pct`/margins already sanctioned for display in
  `ScreeningDossier.tsx`); no strategy param key/value is rendered.
- **Silent degradation**: verified via unit test that `getProvenanceForBot` returns `null` (not a

  Supabase error on the campaign query after a candidate was found. The page only renders
  `BotProvenance` when `provenance` is truthy, so a missing/erroring screening backend leaves the
  rest of the fiche completely unaffected — matches the required behaviour for the current state
  (screening tables not yet created).
- **French/voice**: all user-facing text is French, first person is implicit here (no "on/nous"
  used — the block describes the bot/campaign, not an authorial action, so the 1st-person rule

  `/22\/07\/2026|2026-07-22/` either-format assertion without introducing a second date-formatting

- **Did not modify `src/lib/screening.ts`'s existing exports** — only added the new function;
  `marginLabel`, `getStrategyDossier`, etc. are untouched, so `famille/[base]/page.tsx` and

## Concerns

- `getProvenanceForBot` assumes at most one `screening_candidates` row per `bot_slug`
  (`.maybeSingle()`); if a bot were ever re-screened and produced two candidate rows sharing the
  same `bot_slug`, this would surface as a Supabase "multiple rows" error and the block would
  silently disappear rather than picking one — acceptable given the silent-degrade requirement,
  but worth a `DECISIONS.md`/backend note if that scenario becomes possible (e.g. a bot promoted
  from more than one campaign).
- I could not run `npm run build` (per instructions) or a live Supabase check, so the "returns
  empty/null gracefully once the real screening tables exist but are empty" path is verified only
  by the mocked unit tests, not against a live schema.

## Follow-up: 3 review findings fixed (this session)

### Finding 1 — Supabase errors swallowed silently in `getProvenanceForBot`

Both `error: e1` (candidate lookup) and `error: e2` (campaign lookup) were discarded with
`if (e1 || !candidate) return null` / `if (e2 || !campaign) return null` — a real Supabase error
(missing relation, bad column, RLS block) looked byte-identical to "this bot was never screened".
Added a labelled `console.error` before each `return null`, matching the pattern already used by
`getChangelogForBot` in `queries.ts` (`console.error('[fn]', error.message)` then degrade). The
`null` return and silent page-level degradation are unchanged — only the two call sites that used
to discard `e1`/`e2` now log first.

### Finding 2 — thousands-separator helper was a no-op in `ScreeningDossier.tsx`

Root cause, confirmed by direct codepoint inspection: `ScreeningDossier.tsx`'s private `count()`
used `.replace(/[   ]/g, ' ')` — a character class of **three plain ASCII U+0020 spaces** — against
a string that `toLocaleString('fr-FR')` groups with **U+202F** (narrow no-break space), sometimes
U+00A0. The regex never matched, so the `.replace()` was a pure no-op; the component's own test
(`getByText(/73 744/)`) passed anyway because Testing Library's `getByText` normaliser treats every
Unicode whitespace variant (`\s`, which includes U+00A0/U+202F) as equivalent, so it couldn't
distinguish the broken output from a correctly-formatted one. Verified via hex dump of all three
private copies before touching anything:
- `ScreeningDossier.tsx`: class = `{U+0020, U+0020, U+0020}`, replacement = `U+0020` → no-op (bug).
- `BotProvenance.tsx`: alternation `U+202F | U+00A0`, replacement = `U+0020` → converts to plain space.
- `ScreeningGrid.tsx`: class = `{U+0020, U+00A0, U+202F}`, replacement = `U+202F` → normalises to NNBSP.

Consolidated per the brief into a single exported `count()` in `src/lib/screening.ts`, matching on
`U+00A0`/`U+202F` and normalising to the canonical `U+202F` (this is `ScreeningGrid.tsx`'s existing
— and already correct — behaviour, chosen as the single canonical output since it's what
`toLocaleString('fr-FR')` already emits natively on this runtime, and it's what the third pinned
call site (`ScreeningGrid.test.tsx`, `toBe('73 770')` with a literal U+202F in the test source)
already required). Deleted all three private copies; `ScreeningDossier.tsx`, `BotProvenance.tsx`
and `ScreeningGrid.tsx` now import `count` from `@/lib/screening`.

One consequence flagged explicitly rather than hidden: `BotProvenance.tsx`'s *previous* private
`count()` converted the separator to a plain ASCII space (its own test pinned that with
`toMatch(/73 770 .../)`, ASCII space in the literal) — that was the opposite convention from
`ScreeningGrid.tsx`. Consolidating on the canonical U+202F changes `BotProvenance`'s rendered
separator character (invisible to the eye; still reads as "73 770") but breaks that literal
byte-for-byte pin. Updated `tests/components/BotProvenance.test.tsx`'s one assertion to
`new RegExp(\`73 770 configurations jugées\`)` (explicit ` ` escape, not a raw invisible
character, precisely to avoid re-introducing an invisible-whitespace bug into the test suite
itself). No rendered French copy changed — only this one separator codepoint.

**New test** — `tests/lib/screening.test.ts`, `describe('count', ...)`:
```ts
const NARROW_NBSP = ' '
const ASCII_SPACE = ' '

it('groups thousands with a narrow no-break space, never a plain ASCII space', () => {
  const formatted = count(73770)
  expect(formatted).toBe(`73${NARROW_NBSP}770`)
  expect(formatted).toContain(NARROW_NBSP)
  expect(formatted.includes(ASCII_SPACE)).toBe(false)
})

it('returns the em-dash placeholder for null', () => {
  expect(count(null)).toBe('—')
})
```
Both assertions use explicit `\u` escapes rather than literal invisible characters in the source —
deliberately, since a raw invisible character in a test file is exactly the kind of thing a future
editor (human or agent) could silently mangle back into a plain space without anyone noticing,
which is the entire failure mode this finding is about.

### Finding 3 — `.maybeSingle()` multi-row fragility

`getProvenanceForBot` queried `screening_candidates` by `bot_slug` with a bare `.maybeSingle()`,
which throws a Supabase "multiple (or no) rows returned" error if a bot is ever re-screened into a
second candidate row — silently vanishing the whole provenance block instead of picking one.
Changed the query to `.order('rank', { ascending: true }).limit(1).maybeSingle()`, so it
deterministically takes the best-ranked candidate instead of erroring on more than one row. Pinned
with a new test asserting the mocked query chain receives `order('rank', { ascending: true })` and
`limit(1)`.

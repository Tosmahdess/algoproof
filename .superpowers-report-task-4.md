## Self-review finding (fixed before commit)

The brief's reference `count()` implementation and its own test both used a **regular space (U+0020)** where the character actually needed is the **narrow no-break space (U+202F)** mandated by the task's global constraints ("Large counts use the French thousands separator as a NARROW NO-BREAK SPACE (U+202F)").

Verified byte-for-byte (via `Buffer` inspection, not just visual comparison):
- `D:\brain-vault\.superpowers\sdd\task-4-brief.md` line with `.toBe('73 770')`: the byte between `73` and `770` is `0x20` (plain space) — not `0xE2 0x80 0xAF` (UTF-8 for U+202F).
- The brief's reference `count()` also does `.replace(/ | /g, ' ')` — i.e. it actively **strips out** whatever narrow-no-break-space or NBSP the locale API produces and substitutes a plain space. This directly contradicts the stated requirement and would have shipped the wrong character to the site.

Also verified: this Node runtime's `(73770).toLocaleString('fr-FR')` already emits U+202F natively (checked via codepoint dump), so no replace was strictly required here — but I kept a defensive `replace(/[   ]/g, ' ')` in `count()` so the separator is forced to U+202F regardless of the runtime's ICU data (Node full-icu vs small-icu, or a browser bundle, could differ).

Fixed both sides:
- `count()` now normalizes any of {regular space, NBSP, narrow NBSP} to U+202F.
- The test assertion for `cell-EMAcross-H4-judged` now asserts the actual U+202F character (confirmed via `Buffer` dump: bytes `e2 80 af` sit between `73` and `770`), not the brief's regular-space typo.

This is the only content deviation from the brief's literal listing; everything else (test structure, component structure, testids, wording) matches what was given.
